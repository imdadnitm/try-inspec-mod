# Dependency Management & Constraints

## Overview

This document defines the InSpec Docker profile's dependency strategy: **minimal pinning with intentional commit-hash locking** for deterministic builds.

## Dependency Resolution Strategy

### 1. Minimal Version Constraints (inspec.yml)

**File**: `docker-profile-1/inspec.yml`

```yaml
depends:
  - name: inspec-docker-resources
    url: https://github.com/inspec/inspec-docker-resources.git
    # NO version constraint — allows any commit
```

**Rationale**:
- Early-stage profile (v0.1.0) unlikely to have breaking changes
- inspec-docker-resources is stable, maintained by Chef
- No known compatibility issues with older/newer versions
- Flexibility for users to test different versions if needed

### 2. Commit-Hash Pinning (inspec.lock)

**File**: `docker-profile-1/inspec.lock`

```yaml
lockfile_version: 1
depends:
- name: inspec-docker-resources
  resolved_source:
    url: https://github.com/inspec/inspec-docker-resources/archive/15e068090bf9ec066a1111e13d41c42138b50f1a.tar.gz
    sha256: 5f24bab1f34839a20f9cf43153375d3a26515537fd72319fa5d141e09e5ae030
  version_constraints: []
```

**Pinned Commit**: `15e068090bf9ec066a1111e13d41c42138b50f1a`  
**SHA256**: `5f24bab1f34839a20f9cf43153375d3a26515537fd72319fa5d141e09e5ae030`

**Rationale**:
- Lock file auto-generated by `inspec vendor`
- Ensures deterministic builds across environments
- Users get same inspec-docker-resources version on all machines
- Commit hash + SHA256 = immutable, tamper-evident pinning

## Critical Constraints & Reasoning

### 1. **inspec-docker-resources** is Critical ✅

**Why Critical**:
- Only external dependency
- Provides `docker_image`, `docker_container`, `docker_network` resources
- Without it, all Docker-specific controls fail
- No fallback or alternative available

**Constraint Strategy**:
- ✅ LOCKED to commit hash (prevents surprise updates)
- ✅ NO version constraint in inspec.yml (allow flexibility)
- ✅ Test with latest version periodically (detect breaking changes)

**Update Safety**:
```bash
# Safe: Users can manually test newer version
rm -rf docker-profile-1/vendor
cd docker-profile-1
# Edit inspec.yml to specify version/branch if needed
inspec vendor

# Lock new version
git add inspec.lock
git commit -m "deps: update inspec-docker-resources to <commit>"
```

### 2. **InSpec CLI** is Critical ✅

**Current**: v5.x (latest)  
**Minimum**: v4.0 (estimated, untested with v3)

**Why Critical**:
- Runtime dependency: required to execute profile
- Profile uses DSL syntax that may not work with very old InSpec versions

**No Explicit Constraint** (by design):
- Users should install latest via `brew install inspec` or `gem install inspec`
- Early-stage profile unlikely to break with InSpec updates
- No constraint = simpler for users, simpler for us

**Constraint Strategy**:
- ✅ NO version constraint in profile files (users manage InSpec install)
- ✅ DOCUMENT minimum version if discovered (v4.0+?)
- ✅ TEST with new InSpec releases in CI/CD (future)

### 3. **Ruby** is Critical ✅

**Current**: 2.7-3.2 (via InSpec)  
**Provided By**: InSpec package

**Why Critical**:
- InSpec DSL is Ruby
- Profile contains Ruby code (albeit minimal in example.rb)

**No Explicit Constraint** (by design):
- InSpec manages Ruby version dependency
- Users install InSpec, Ruby comes with it
- Profile doesn't use Ruby features unavailable in supported versions

**Constraint Strategy**:
- ✅ NO version constraint (InSpec handles it)
- ✅ Assume InSpec v4.0+ means compatible Ruby

### 4. **Docker Daemon** is Critical ✅

**Current**: 20.10+ (tested with latest)  
**Minimum**: 18.0 (estimated, untested)

**Why Critical**:
- Runtime dependency: profile queries live Docker daemon
- Controls use `docker ps`, `docker image ls`, etc. via API
- Without Docker, profile cannot execute

**No Constraint in Profile** (expected):
- Docker is user-managed infrastructure, not a package dependency
- Profile documents this as prerequisite

**Constraint Strategy**:
- ✅ DOCUMENT as prerequisite in build-test.md
- ✅ TEST with multiple Docker versions (future: CI/CD matrix)
- ✅ Note any version-specific features in controls

## How Pinning Works in Practice

### User Workflow: Locked Builds

```bash
# 1. Clone repository
git clone https://github.com/imdadnitm/try-inspec-mod.git
cd try-inspec-mod

# 2. Fetch dependencies (uses inspec.lock)
cd docker-profile-1
inspec vendor

# 3. Check what was fetched
ls -la vendor/
# Outputs: inspec-docker-resources @ locked commit

# 4. Run profile
inspec exec .
# Uses locked version of inspec-docker-resources

# All users get SAME inspec-docker-resources version ✅
```

### Developer Workflow: Updating Dependencies

```bash
# 1. Update inspec.yml (optional constraint change)
# Example: add version constraint if needed
# - name: inspec-docker-resources
#   url: ...
#   branch: main  # or version, tag, etc.

# 2. Re-vendor to resolve new version
rm -rf vendor inspec.lock  # Start fresh
cd docker-profile-1
inspec vendor

# 3. New inspec.lock auto-generated with new commit hash

# 4. Review & commit
git diff inspec.lock
# Shows: old commit hash → new commit hash
git add inspec.lock
git commit -m "deps: update inspec-docker-resources to <new-commit>"

# 5. Push for CI/CD testing
git push

# CI/CD tests validate new version doesn't break controls
```

## Dependency Health & Monitoring

### Detection: When to Update

| Signal | Action | Criticality |
|--------|--------|------------|
| **Security issue** in inspec-docker-resources | Update immediately | 🔴 CRITICAL |
| **Bug fix** for Docker API compatibility | Update soon | 🟡 MEDIUM |
| **New feature** in inspec-docker-resources | Optional, update on schedule | 🟢 LOW |
| **InSpec major version** released | Test & update in CI/CD | 🟡 MEDIUM |
| **InSpec patch version** released | Encourage users to upgrade | 🟢 LOW |

### Manual Check: Dependency Status

```bash
# 1. Check current lock file
cd docker-profile-1
grep "sha256" inspec.lock
# Output: sha256: 5f24bab1f34839a20f9cf43153375d3a26515537fd72319fa5d141e09e5ae030

# 2. Check for updates
inspec exec . --inspect
# Shows which versions are available (if any)

# 3. Visit GitHub repository
open https://github.com/inspec/inspec-docker-resources
# Check "Releases" tab for new versions
# Check "Commits" tab for latest commit hash

# 4. Test newer version (if available)
rm -rf vendor inspec.lock
# Edit inspec.yml to use new version/branch/commit
inspec vendor
inspec exec .  # Run controls to verify compatibility

# 5. If all tests pass, commit new lock file
```

### Automated Monitoring (Proposed)

```yaml
# .github/workflows/dependency-check.yml (example)
name: Dependency Updates
on:
  schedule:
    - cron: '0 0 * * 0'  # Weekly

jobs:
  check-updates:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Check inspec-docker-resources updates
        run: |
          cd docker-profile-1
          # Fetch latest from GitHub
          git clone --depth 1 https://github.com/inspec/inspec-docker-resources.git check-repo
          LATEST_COMMIT=$(cd check-repo && git rev-parse HEAD)
          CURRENT_COMMIT=$(grep 'archive' inspec.lock | grep -oE '[a-f0-9]{40}' | head -1)
          
          if [ "$LATEST_COMMIT" != "$CURRENT_COMMIT" ]; then
            echo "Update available: $CURRENT_COMMIT → $LATEST_COMMIT"
            # Notify maintainers
          fi
```

## Minimal Pinning Principle

This profile follows **minimal pinning**: constraints are loose unless there's a proven compatibility issue.

### Benefits

✅ **Flexibility** — Users can test with different versions  
✅ **Simplicity** — Fewer constraints to manage  
✅ **Early stage** — Less likely to have breaking changes  
✅ **Maintainability** — Easier for contributors  

### Trade-offs

⚠️ **Non-determinism risk** — If user runs without lock file (unlikely)  
⚠️ **Surprise updates** — If user manually updates and doesn't run tests  
⚠️ **Compatibility gaps** — Must catch issues via testing  

### Mitigation

- ✅ Lock file enforces determinism for typical workflow
- ✅ Documentation & build-test.md guide users
- ✅ CI/CD (future) tests on multiple versions
- ✅ Clear issue template for compatibility reports

## Adding New Dependencies

When adding external dependencies (Ruby gems, other profiles):

### 1. **Prefer minimal constraints**
```yaml
# ✅ Good: Minimal constraint
depends:
  - name: some-profile
    url: https://...
    # No version specified → latest

# ❌ Avoid unless necessary: Tight constraint
depends:
  - name: some-profile
    url: https://...
    version: "~> 1.2.3"  # Only if compatibility tested
```

### 2. **Always vendor after adding**
```bash
cd docker-profile-1
inspec vendor  # Generates new inspec.lock
git add inspec.lock
git commit -m "deps: add some-profile"
```

### 3. **Document why** (in commit message or DEPENDENCIES.md)
```
deps: add some-profile for advanced Docker compliance

Rationale: Provides built-in controls for container security scanning.
Constraint: None (early-stage, uses latest).
```

### 4. **Test thoroughly**
```bash
inspec exec .  # Ensure profile runs without errors
```

## Emergency Rollback

If a dependency update breaks the profile:

```bash
# 1. Identify the problematic commit
git log --oneline -n 10 inspec.lock
# Shows recent changes to lock file

# 2. Revert to previous version
git revert <commit-hash>
# or
git checkout <previous-commit> docker-profile-1/inspec.lock

# 3. Re-vendor
cd docker-profile-1
rm -rf vendor
inspec vendor

# 4. Verify fix
inspec exec .

# 5. Commit rollback
git add inspec.lock
git commit -m "deps: rollback inspec-docker-resources (broke X control)"

# 6. Open issue to investigate
# Why did new version break? Can we fix it? Is it a profile bug?
```
